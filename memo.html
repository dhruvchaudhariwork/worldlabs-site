Research memo

Agents that finish the job

A research agenda for long-horizon work in game engines and creative tools.

World LabsOctober 14, 2026

Abstract

Useful agents need to carry an assignment through many dependent decisions. In game development, that means connecting code, assets, scenes, and live behavior while preserving the systems already in place. A plausible script or a convincing screenshot captures only part of that work.

World Labs is building environments to train and evaluate this capability. Our research direction combines tasks inside game engines, verification of the resulting experience, and human demonstrations and feedback. This memo sets out the motivation and proposed design principles for that work. The longer-horizon task suite and methodology are under development.

Why interactive worlds

A game is a system whose parts must agree. Geometry affects movement. A script changes scene state. An interface communicates what the player can do. A feature can look correct in the editor and still fail when the game runs, when a player repeats an action, or when another system changes the same object.

We think this makes game engines useful environments for studying sustained agent work. They bring software, spatial structure, and interaction into a shared project. Tasks can require an agent to inspect an unfamiliar world, make a plan, modify several kinds of artifacts, observe the consequences, and revise its approach.

Existing research provides important foundations. SWE-bench evaluates changes to existing repositories against real software issues.[1] OSWorld provides computer tasks spanning applications, with explicit starting states and execution-based evaluation.[2] In Roblox Studio, OpenGameEval checks both edited scenes and behavior in play sessions.[3]

Our interest is in extending connected work across tools and over longer sequences of decisions. We’re developing tasks across Roblox Studio, Unity, Unreal Engine, Godot, and other game engines. Our longest-horizon tasks will extend into creative tools such as Blender, where an asset must remain useful after it leaves the application that created it.

The unit of success is a functioning result, with the rest of the game still intact.

One connected assignment

Consider an illustrative task: add a gate that opens after the player completes an existing objective. Create the gate asset in Blender, integrate it into the level, implement its behavior, and test the experience. Existing movement, objectives, and progression must continue to work.

The agent first needs to understand the project. Where is objective completion recorded? Which code owns the gate’s state? What dimensions fit the passage? How are collisions handled? These questions determine whether later changes can fit into the existing game.

A successful export is only an intermediate result. The imported gate may have the wrong pivot. Its visual opening may leave an invisible collider in the way. An event handler may work once and fail after a reset. Fixing those problems may require returning to an earlier tool and then checking the downstream changes again.

This is what we mean by a long horizon: decisions remain relevant after the agent has moved on. Duration and action count help describe the workload, but the research challenge is preserving intent and constraints across dependencies, interruptions, and revisions.

Verifying the whole result

Verification should be designed alongside the assignment. A useful task specification identifies the requested change, the starting project, the available tools, and the behavior that must remain intact. It also defines what evidence is sufficient to call the work complete.

For the gate example, checks could inspect the imported object and its configuration, exercise the objective-to-gate interaction in a running session, and rerun the existing progression path. The evaluation should distinguish a correct feature from a solution that makes the test pass by removing the obstacle, disabling collisions everywhere, or bypassing the objective.

We propose evaluating several dimensions together:

Completion
Does the delivered project satisfy the requested behavior under the task’s stated conditions?
Preservation
Do the required existing behaviors still work after the changes?
Consistency
Does the agent succeed across independent runs and controlled variations of the starting state?
Recovery
Can it diagnose an observed failure, revise its approach, and reach a verified result?
Cost and intervention
How much time, tool use, and human assistance does completion require?

These dimensions need explicit reporting rules. Completion should be measured over all assigned tasks; partial progress and regressions should be reported separately. Repeated attempts should use reset environments and a declared budget. Infrastructure failures, model failures, and human interventions need separate records.

Reproducibility also depends on the environment: engine and tool versions, project assets, random seeds where applicable, and the evaluator itself. We intend to use held-out projects and variations to test whether an agent can handle unfamiliar situations. Evaluation checks should be protected from modification by the agent and reviewed for shortcuts and incomplete coverage.

No finite test suite can establish that every aspect of a game is correct. Automated checks can cover stated requirements, while human review can examine qualities that are difficult to reduce to a deterministic assertion. Both need a defined scope.

Learning from human judgment

The final artifact tells us what was delivered. A trajectory can show the observable work that led there: what the developer inspected, which tools they used, what changed, what failed, and how they responded.

We’re also developing human-data projects across game engines and browser games, including WebGL experiences. Expert demonstrations, critiques, comparisons, and revisions can capture decisions about development, design, and playtesting. For the gate task, a reviewer might explain why an interaction is confusing, compare two implementations, or revise an animation so the player can read its state.

Our proposed data design connects feedback to the relevant project state and artifact. A critique should identify the behavior it refers to. A revision should preserve the before-and-after versions. A demonstration should include the observations and checks available to the expert, with rationale where the expert chooses to provide it.

These records could support supervised learning, preference learning, reinforcement learning, and evaluation. Whether a particular form of feedback improves sustained execution is an empirical question. We plan to study that relationship while keeping training material separate from held-out evaluation tasks.

The research agenda

World Labs’ current direction has two connected parts: environments that demand sustained execution, and evidence that lets us judge the resulting work. Interact Bench presents building and debugging tasks; its full results and methodology are available separately. Worldline Bench is under development around extended assignments with many dependent steps.

For this longer-horizon work, the questions we want to investigate include:

  • How does reliability change as dependencies accumulate across assets, code, scenes, and tools?
  • Which observations, checkpoints, and recovery behaviors help an agent preserve earlier work?
  • Which combinations of executable feedback and expert judgment improve the quality of the final experience?

Progress will require careful task construction as well as better agents. A longer script of trivial actions would tell us little about maintaining a coherent project. Task difficulty should come from meaningful constraints, incomplete information, and changes whose consequences must be discovered and checked.

Game-engine performance also has limits as evidence. It does not by itself establish reliability in other software, physical environments, or every creative workflow. Transfer across engines and tools must be measured. Our aim is to make the work and its outcomes inspectable enough that these questions can be tested.

We want to build toward agents that can take responsibility for a whole assignment: understand the goal, carry the work across systems, recover when something goes wrong, and deliver a result that holds up when used.
